# 经典关卡接入：地形、敌军替换、事件与任务

状态：**基础任务/副本接入已实现**（60 张经典地图、78 个任务、18 个连战副本）；门/宝箱/地图变化/增援/剧情事件执行器与专用 `validateScenarioBattle()` 仍为待办。核对基线为当前代码及 `content/scenarios/classic-maps-v1/catalog.json`。

采用原则：保留原地图的布局和战术用途；敌军优先使用项目中对应的可用职业，没有对应职业就换成项目已有职业。新增功能集中在地图交互、事件和任务接入，不要求补齐原作全部职业、魔法、技能或剧情。

**选图约束：只采用可正常编队出战的常规全灭、击败首领、撤退或占领图。排除单人/双人试炼、少量单位决斗，以及坚守、护送、收集、孵化等特殊任务地图。** 本批已替换封印终章、烈火勇者罗兰与坚守关、圣魔魔王单场及特殊任务关。烈火同章两种路线仅在布局确实不同的情况下各算一张，不把难度变体计成不同地图。

## 2. 地块映射与缺失功能

地形显示和地形功能分开处理：地面负责移动/战斗加成，门、宝箱等放在物件层，覆盖物或机关负责阻挡和地图变化。原作编号应以作品为命名空间；下表使用当前包的共享符号注释，实际通行规则仍须核对该作品职业记录。

### 2.2 必需的物件功能

- [ ] **门**：关/开状态、占用与通行、可见交互范围、开门动作和行动消耗、关联地图变化。
- [ ] **开锁策略**：首版可以统一使用“相邻单位互动开启”，也可按关卡限制盗贼；逐图固定策略。现有项目没有门钥匙/开锁器，不把源钥匙ID当作当前可用道具。
- [ ] **宝箱**：一次性开启、物品或金币奖励、空箱样式、重复交互拒绝；奖励写入战利品账本后由结算入库。
- [ ] **破坏物**：独立于敌军的目标、HP、伤害规则、破坏后地图变化；不能把墙伪装成计入全灭目标的敌人。
- [ ] **村庄/民房**：访问一次、访问/破坏互斥、项目奖励和事件标记；原剧情对白可替换为项目文本。
- [ ] **机关与桥**：开关、触发区域、顺序、已触发标记、变化后通行与路径刷新。
- [ ] **迷雾/室内可见性**：若采用相关关卡，补充敌军可见集合、视野、探索信息和前端遮罩；否则在该图配置明确关闭迷雾，不能宣称完整保留。

### 2.3 地图验证不能沿用随机生成器全部限制

现有 `BattleMap v3` 要求每方1–8个出生点、仅一个制压目标、目标不与出生点重叠，并检查四类移动的所有可通行区域相连。经典关卡存在更多敌人、王座首领、封闭房间、飞行区域和事件开启通路。

- [ ] 新增 `validateScenarioBattle()`，不放宽 `validateMap()` 来迁就导入地图。
- [ ] 校验玩家出击区、敌军实际出生点、物件、目标和各事件阶段的可达性；封闭房间允许通过已声明的开门/地图变化事件解锁。
- [ ] 同一格的“王座地形 + 首领”合法；两个存活单位重叠仍非法。
- [ ] `off-map`/`unresolved` 源记录不能直接生成战斗单位；在适配文件注明其过场用途、坐标覆盖或排除理由。
- [ ] 烈火终章保存有地图外宝箱记录 `(18,19)`，必须审查并显式排除/重定位，不能自动裁到地图边缘。
- [ ] 玩家出击人数与敌军数量独立配置；不把经典地图敌军静默裁到8人。出击人数上限与文档20中的关卡等级上限一并落地。

## 3. 敌军职业：优先对应，缺少则替换

映射键使用 `(source.game, effectiveClassId)`。显示符号只是注释；不能用三作通用的数字职业ID，也不能只判断 `CLASSES[id]` 是否存在。

最终目标职业必须同时满足：属于 `CATALOG_CLASS_IDS`，且 `classUnavailableReason(id) === null`。退役职业、带待实现机制的职业和旧存档别名不能作为新内容的默认目标。

## 5. 事件如何接入

### 5.1 使用“源素材 + 项目适配配置 + 战斗执行状态”三层

保留 `scenario.json` 作为源素材。新增项目适配文件，例如 `content/scenarios/adaptations/gba-classics-v1/<scenarioId>.json`，以素材文件的SHA-256绑定版本；不直接编辑源记录来隐藏替换。

适配文件至少包括：

- `scenarioId/sourceSha256/adapterVersion`：素材和适配版本。
- `initialEnemyGroupIds/sourceVariant`：明确的一套初始敌军及难度，不合并所有变体。
- `deployment/levelPolicy/goal/turnLimit`：项目出击区、人数、等级、目标和时限。
- `terrainMap/classMap/itemMap/aiOverrides`：映射与逐单位覆盖。
- `objects/mapChangeBindings/waves/triggers`：交互物件、变化、增援和条件。
- `rewards/drops/requiredFeatures/excludedSourceRecords`：战利品、功能门槛和有理由的排除记录。

这些是待实现字段示意，不是现有可直接读取的配置API。

### 5.2 事件模型

| 触发条件 | 可复用信息 | 项目动作 |
| --- | --- | --- |
| 战斗开始 | 开场脚本和初始表 | 建立初始地形/物件、敌军、NPC、事件标记 |
| 指定回合的指定阶段 | `events.turn` + 适配配置 | 生成一组增援、开关旗标、变化地图 |
| 某单位行动后进入区域 | 区域记录、坐标边界、原脚本 | 一次性/持续触发警戒与增援 |
| 开门/开箱/访问/踩机关 | `objects`、地点事件、变化表 | 更新物件、地形、奖励和事件标记 |
| 单位被击败/关键目标达成 | 战斗事件 + 源条件 | 切换阶段、解锁门、刷新目标或结束战斗 |
| 对话/救援/加入 | 交谈记录与适配角色ID | 项目NPC/招募流程；不直接生成原作永久角色进玩家名册 |
| 多王座占领 | 制压地点与原事件关系 | 记录制压进度和目标集合，全部完成后判胜 |

- [ ] 新建受限的声明式事件执行器，例如 `backend/common/scenarios/runtime.ts`；不在服务端执行ROM机器码或任意脚本字符串。
- [ ] FE6/FE7当前静态扫描到首个终止指令；FE8静态解码也没有执行分支、存档、随机数和ASM。关键事件逐图人工审核并转成声明式规则，不宣称可自动完整翻译。
- [ ] 将每条关键源事件标为“已转译 / 明确替换 / 不采用 / 待确认”，保存源地址、目标规则及理由；未决关键事件阻止发布。
- [ ] 通用事件只调用项目动作：生成单位、改变物件、应用地图变化、设置标记、记战利品、设置目标、结束战斗等。
- [ ] 对象/阶段/角色使用稳定ID，不能把原作人物ID直接当作当前战斗单位ID。

### 5.3 与战斗循环的顺序

建议顺序：

1. 读取并校验素材与适配配置，应用开场变化，摆放玩家/敌军/NPC，触发开场事件。
2. 阶段开始时执行该阶段的增援/地形事件，再处理现有地形回复、NPC和可行动状态；具体先后写成规则并回归验证。
3. 单位移动及动作结算后，执行区域、死亡、物件与目标事件。
4. 事件产生的死亡/阶段变化继续结算至稳定状态，然后统一检查胜负。
5. 通过既有API保存状态、动作和战斗事件，前端按结果渲染。

现有 `checkResult()` 会在敌人清零时直接判全灭获胜。接入后必须考虑尚未触发的必需增援和目标进度；也不能因为守点敌人还在过场模板里就一直无法获胜。

- [ ] 增援配置声明首次可行动阶段；避免玩家阶段末刷怪立刻偷袭的无提示行为。
- [ ] 出生格被占时按规则等待或选固定备用格，稳定顺序、可回放；不能随机挤走现有单位或无限重试。
- [ ] 地图变化只覆盖非 `null` 单元。若变化使站立格不可通行，适配规则必须明确延迟、合法迁移或拒绝该变化。
- [ ] 给事件队列设置最大连锁次数，防止条件相互触发而死循环。
- [ ] 胜负判定不得先于必要的死亡/增援/目标事件；撤退和多占领点单独验收。

### 5.4 存档、回放与奖励

- [ ] 为战斗增加场景运行状态：场景/适配版本、标记、已触发事件ID、物件状态、波次状态、目标进度与战利品账本。
- [ ] 新事件类型覆盖开门、开箱、物件损伤、地形变化、增援、目标改变和领取战利品；同步前后端与回放。
- [ ] 回放从固定 `initial` 状态、素材/适配版本及动作序列重建；历史关卡不跟随最新版配置改变。
- [ ] 奖励和掉落在现有结算路径统一入库，胜利/撤退/失败分别定义保留规则；重复结算使用稳定奖励ID去重。
- [ ] 序列化、API返回和前端共享类型一起升级。涉及引擎语义变化时明确引擎版本兼容，保留旧回放路径。

# 33 · 旧存档日历迁移

更新：2026-10-18。工具：`backend/api/migrate-save.ts`，核心及文件回归：`save-migration.ts`／`save-migration.test.ts`。需要Node.js 22.18+，本次验证使用22.22.0。

当前存档以`save_metadata`记录`schema_version=1`、`calendar_days_per_year=500`和最近迁移来源／时间／备份路径。新数据库自动初始化；已有人物却没有日历标记的旧文件启动时返回`SAVE_CALENDAR_MIGRATION_REQUIRED`。程序不会根据日期大小猜旧档是一年120日还是500日。

## 使用流程

先根据生成存档的代码版本确认来源。旧120日档选`120`；已经运行500日历、仅缺版本标记的档选`500`，后者只采纳版本、提升玩家版本号，不放大日期／年龄／活动。一个文件只能有一种来源日历；混合导入的数据应先在副本中核对修复，不可盲选。

从仓库根目录运行，先预演，检查玩家日期、行数、`notes`与`blockers`：

```powershell
$savePath = 'D:\game-data\agent-tactics.db'
npm --prefix backend run migrate-save -- --db $savePath --from-year-days 120
# 已是500日历但缺标记时：
npm --prefix backend run migrate-save -- --db $savePath --from-year-days 500
```

默认只读，不创建备份、不写入数据库。预演也会解析实际待迁字段并检查SQLite完整性；非法JSON、负日期、孤立归属或索引列／JSON不一致会报错退出，不自动删除或猜测修复。使用副本调查异常，保留原档。

跨日历迁移前，在旧服务中结束／撤退所有进行中的战斗、连续远征与年度赛事，再停止API和Worker。未完成活动会返回`blocked`，退出码2；不会迁一半、自动判负或消耗物品。运行中的生产、派遣及尚未开始的普通竞技场进攻可迁移。

确认预演后，对停服的同一文件应用。备份必须是新的路径，工具拒绝覆盖已有文件：

```powershell
$backupPath = 'D:\game-backups\agent-tactics-before-calendar.db'
npm --prefix backend run migrate-save -- --db $savePath --from-year-days 120 --apply --backup $backupPath
# 只采纳500日旧档时，将120替换为500。
npm --prefix backend run migrate-save -- --db $savePath --from-year-days 120
```

省略`--backup`会生成同目录的`<db>.pre-calendar-<时间戳>.db`，实际路径在结果中返回。成功返回`applied`；再次执行返回`up-to-date`，即使误保留`--from-year-days 120`也不会再放大。普通错误退出码1，正常预演／成功／已最新退出码0。

完成后使用新版本打开数据库、查询状态，再启动同一版本的API／Worker。仍需按实际部署环境验证恢复和权限，本次没有可用业务旧档，未对生产数据执行迁移。

## 日期和进度如何换算

旧历每季30日／每年120日，新历每季125日／每年500日。每季首尾按比例对齐：`floor(day/30)*125 + round((day%30)*124/29)`。

| 旧绝对日 | 新绝对日 | 保持的含义 |
| ---: | ---: | --- |
| 0 | 0 | 新年第一日 |
| 29 | 124 | 第一季末、普通竞技场日 |
| 30 | 125 | 第二季第一日 |
| 119 | 499 | 第一年的最后一日 |
| 120 | 500 | 第二年的第一日 |
| 239 | 999 | 第二年的最后一日 |
| 960 | 4000 | 八年后，不压回主线内 |

年份、季度、季度消费／小游戏次数、酒馆候选与商店刷新计数保持对应关系。角色先用旧120日制和旧年龄锚点还原迁移当日的年龄天数，再乘500／120并把锚点移到新当日；缺失锚点时用旧入队日及基础年龄。主角不叠加流逝年龄。整岁、寿命年数、实例属性／成长、学习、装备耐久、剩余次数和状态保持，不重新掷点、补EXP或自动重算死亡。

| 数据 | 迁移规则 |
| --- | --- |
| 玩家、入队／退役／轮回日、纪念日期 | 按季度映射；玩家版本号加1 |
| 未领取生产、运行中派遣 | 围绕玩家新当日平移开始／结束日，剩余行动日和原工作天数相同；保持工位、人员锁、奖励、是否已结算 |
| 已结算生产／派遣 | 结束日映射到新历，开始日按原实际工作天数回推；派遣结果记录日映射，既有收益不重算 |
| 竞技场日、快照、战报结束日／所属竞技场日 | 索引列与JSON同时改；快照的系统日期标签同步，冻结单位、名单、BAN与已打进攻不改 |
| 年度赛事 | 保留届次、签表、名单、种子、终态与已领奖键；冻结名册若有年龄锚点则按旧历迁移 |
| 轮回记录 | 年龄天数换算，成长分配与轮次保持 |
| 报价 | 120日迁移删除旧报价；500日采纳靠玩家版本号变化拒绝旧报价 |

**年度窗口使用当前规则：每年末18日。旧历未报名窗口不结转、不补赛、不自动延长到4018日。** 例如旧D120转为D500，已结束第1届仍结束，下一次新开窗为D982；不能因换日历重领第1届奖励。预演`notes`也明确提示这条策略。

全部记录ID保持稳定，即使旧ID带日期；不能重新生成ID或种子，避免改掉冻结结果或断开引用。`saveSnapshot`按已有玩家／日期复用旧ID，后续保存不会产生第二条同日快照。

金币、公共经验、库存、声望（含超过500的旧值）、任务完成／领奖、限量物品、传承关系、账号令牌／会话、现实月榜及真实时钟不换算。战斗`initial`／`state`、随机数、动作、规则／目录版本和原实际耗日冻结不改。

事件、outbox、Agent备注和命令收据保持原始历史载荷／文字，其中可能保留旧日数字。收据重试仍返回原结果，随后通过`GET_STATE`读取当前日历；不要把收据历史响应当作新的服务器状态。迁移来源记在metadata与备份中，便于核对历史语义。

## 备份、回滚与并发

应用先用SQLite `VACUUM INTO`生成独立一致备份，包含已经提交但仍在WAL中的页面；不会把一个活动主文件的裸拷贝当作完整备份。随后取得`BEGIN IMMEDIATE`锁，核对`PRAGMA data_version`未在备份期间被其他连接改变，再重建迁移计划。所有数据和metadata在一项事务中提交；失败全部回滚。提交前后都执行完整性／外键检查。

仍须停服；若检测到其他连接提交，工具拒绝应用，保留备份以便调查，需重新预演并使用新备份路径。工具不负责在线迁移或调度运行中的服务。

回滚时停API／Worker，将当前`.db`、`.db-wal`、`.db-shm`作为一组移到留档目录，再把独立备份复制到原数据库路径。120日备份须由相应旧版本读取或重新经过此工具迁移。回滚会撤销备份之后的新写入，恢复前先导出需保留的数据；保留来源备份和应用报告，禁止混用新旧WAL文件。
